# Calories Bot: технічна специфікація наступної версії

**Аудиторія:** розробники та QA

**Статус:** погоджено для реалізації

**Дата:** 8 серпня 2026 року

## 1. Призначення документа

Документ описує зміни наступної версії поверх чинної реалізації та вимог із
`docs/PRODUCT.md` і `docs/TZ.md`.

Незмінними залишаються:

- invite-only доступ і перевірка `telegram_user_id` до завантаження фото, LLM та
  персональних сховищ;
- окремий Google Spreadsheet і каталог фото для кожного користувача;
- персональний `day_start` у глобальному `APP_TIMEZONE`;
- захист від повторного запису за `telegram_message_id`;
- перевірюваний запис у Google Sheets;
- безпечне й ідемпотентне видалення прийому;
- чинні адміністративні сценарії.

## 2. Архітектурний принцип

LLM використовується лише там, де потрібні семантичне розуміння, візуальне
розпізнавання або приблизна оцінка. Усе, що можна надійно отримати правилом,
словником, схемою, формулою або запитом до збережених даних, виконується
детермінованим кодом.

### 2.1. Відповідальність LLM

- визначити, чи описує повідомлення з’їдену їжу;
- визначити назву страви й явно названі складники;
- проаналізувати фото;
- витягти назву та калорійність на 100 г з етикетки;
- оцінити відсутню порцію або вагу;
- оцінити відсутню калорійність;
- зіставити зафіксовані джерела з відповідними складниками;
- повернути лише структурований об’єкт аналізу.

### 2.2. Відповідальність застосунку

- доступ, команди й стани діалогу;
- нормалізація однозначних чисел та одиниць;
- фіксація явних значень і їхніх позицій у тексті;
- пріоритет тексту користувача над фото та оцінкою;
- перевірка структурованої відповіді LLM;
- примусове накладання явних значень після LLM;
- визначення ознак `≈` за походженням даних;
- усі калорійні розрахунки й округлення;
- денні та тижневі підсумки;
- зберігання й застосування денної цілі;
- форматування Telegram-відповідей і повідомлень про помилки;
- збереження, дедуплікація та видалення даних.

LLM не повертає готові Telegram-повідомлення, калорії позиції, денний підсумок
або тижневу статистику.

## 3. Обробка запиту на їжу

### 3.1. Послідовність

1. Перевірити приватний чат, користувача та статус доступу.
2. Перевірити `telegram_message_id` у персональному Spreadsheet.
3. Для фото завантажити найбільший доступний Telegram-розмір лише після кроків
   1–2.
4. Детерміновано нормалізувати текст або caption.
5. Зафіксувати всі явні значення як авторитетні джерела.
6. Викликати LLM зі структурованою схемою, нормалізованим текстом, переліком
   джерел і, за наявності, фото.
7. Перевірити схему й повторно накласти авторитетні значення.
8. Виконати доменну валідацію.
9. Детерміновано розрахувати калорії.
10. Зберегти один рядок і перевірити результат запису.
11. Сформувати компактну відповідь із актуальним денним підсумком і ціллю.

На кроках 4–9 жодна помилка не повинна створювати рядок. Чинна поведінка для
невизначеного результату запису в Google Sheets зберігається.

### 3.2. Детермінована нормалізація

До LLM код має:

- перетворювати підтримувані українські й російські числа словами на цифри;
- нормалізувати українські, російські та латинські варіанти грамів;
- нормалізувати `кк`, `ккал`, `kcal` і вирази `на 100 г`;
- перетворювати `#120` і `120#` на канонічне `120 ккал/100 г`;
- розпізнавати явні ваги й калорійність на 100 г;
- присвоювати кожному явному значенню стабільний source ID та позицію;
- зберігати оригінальний текст окремо від нормалізованого;
- відхиляти нульові й десяткові явні значення згідно з поточним контрактом.

Число без одиниці в позиції, яку чинний продуктовий контракт визначає як вагу,
детерміновано означає грами. Числа в конструкціях `2 яйця`, `піца 30 см` та
подібних не можна перетворювати на вагу.

Нормалізатор не повинен вгадувати склад страви, калорійність або сенс
неоднозначної побутової порції.

### 3.3. Пріоритет джерел

Для ваги застосовується порядок:

1. явне значення в тексті користувача;
2. точне детерміноване правило або версійований довідник порцій;
3. візуальна оцінка LLM.

Для калорійності застосовується порядок:

1. явне значення в тексті користувача;
2. значення, прочитане з етикетки;
3. значення з перевіреного довідника продуктів, якщо такий буде додано;
4. оцінка LLM.

Явне значення обов’язково використовується рівно один раз і не може бути
замінене відповіддю моделі. Невідомий, повторно використаний або пропущений
source ID є помилкою аналізу.

Невеликий довідник типових порцій допускається лише для стабільних і
перевірених відповідностей, наприклад середньої ваги одного яйця. Зіставлення
має бути точним за підтримуваним псевдонімом; невпевнене зіставлення переходить до
LLM, а не застосовує випадкове правило.

## 4. Контракт LLM

### 4.1. Вхід

LLM отримує:

- системний промпт із правилами аналізу;
- нормалізований текст або нейтральну інструкцію для фото без caption;
- список авторитетних джерел з ID, типом, значенням, позиціями та фрагментом
  тексту;
- не більше одного фото.

Явний текст має пріоритет над фото. Промпт повинен окремо містити приклади:

- точної ваги й оціненої калорійності;
- побутової порції;
- складеної страви;
- фото готової страви з caption і без нього;
- етикетки з калорійністю;
- повідомлення, яке не описує їжу.

Промпт не повинен просити модель рахувати калорії позицій або підсумки.

### 4.2. Структурована відповідь

`FoodAnalysis` залишається строгою Pydantic-схемою. Для кожної позиції потрібні:

- `name`: коротка українська назва;
- `weight_g`: вага для внутрішнього розрахунку;
- `kcal_per_100g`;
- `weight_source_id` і `kcal_source_id` для явних текстових джерел;
- походження ваги й калорійності;
- необов’язкове коротке представлення порції для UI, наприклад `2 шт.` або
  `1 тарілка`.

Рекомендовані значення походження:

```text
user_text
deterministic_reference
image
model_estimate
```

Поля походження для `user_text` не приймаються на довіру: їх підтверджує
source ID. Для старих рядків `items_json` нові поля мають безпечні значення за
замовчуванням.

Назви й UI-представлення очищаються від зайвих пробілів, обмежуються за
довжиною та екрануються під час Telegram-форматування.

### 4.3. Побутові порції

Для `2 яйця` детермінований попередній обробник зберігає число та вихідну одиницю, а
вага береться з точного довідника або оцінюється LLM. UI може показати:

```text
Яйця ≈140 кк = 2 шт.
```

Для нечітких порцій на кшталт `тарілка борщу` чи `жменя горіхів` LLM оцінює
внутрішню вагу. Фінальний текст не повинен створювати видимість точної ваги,
якщо користувач її не задавав.

### 4.4. Фото

Для фото готової страви LLM визначає їжу та оцінює відсутні параметри. Caption
проходить той самий детермінований попередній обробник, що й звичайний текст.

Для етикетки LLM витягує лише потрібні для цього продукту назву та
калорійність на 100 г. Якщо caption не містить явної кількості, порція
оцінюється без додаткового Telegram-діалогу.

Застосунок не покладається на арифметику, готову відповідь або підсумки з фото.

## 5. Постобробка і валідація

Після LLM застосунок має:

1. Перевірити Pydantic-схему та узгодженість `is_food`, `meal_name`, `items`.
2. Перевірити, що кожен явний source ID використаний рівно один раз і для поля
   правильного типу.
3. Примусово замінити модельні вагу та калорійність значеннями з source ID.
4. Визначити походження й приблизність кожного поля.
5. Перевірити додатні та правдоподібні числові значення.
6. Обмежити кількість позицій і довжину текстових полів документованими
   константами.
7. Відхилити порожні назви та очевидне дублювання однакових позицій, якщо воно
   не випливає з тексту.
8. Лише після цього розрахувати калорії.

Межі правдоподібності мають бути консервативними, зберігатися як іменовані
константи й мати unit-тести. Значення поза межами не можна мовчки обрізати.
Результат відхиляється без запису.

Один контрольований повтор LLM-запиту допустимий лише для виправлення
структурованої відповіді або source ID. Повтор не повинен змінювати явні дані
користувача. Після повторної помилки повертається стабільне повідомлення про
невдалий аналіз.

## 6. Розрахунки та `≈`

Усі розрахунки виконуються кодом:

```text
item_kcal = weight_g × kcal_per_100g / 100
meal_kcal = сума item_kcal
```

Округлення залишається `ROUND_HALF_UP` до цілого для UI. Денний і тижневий
підсумки потрібно рахувати з точних збережених значень і округлювати після
сумування.

Правила `≈`:

- `user_text` — без `≈`;
- `image`, `deterministic_reference` і `model_estimate` — з `≈`;
- результат позиції має `≈`, якщо приблизна вага або калорійність;
- загальна калорійність складеної страви має `≈`, якщо приблизна хоча б одна
  позиція;
- LLM не визначає фінальне відображення `≈`.

## 7. Форматування відповіді

Формування відповіді є повністю детермінованим і HTML-безпечним.

Одна позиція:

```text
Яблучні оладки ≈110 кк = 50 г × ≈220 кк/100 г

За день: 860 кк
```

Кілька позицій:

```text
Перекус ≈230 кк
• Яблуко ≈80 кк = ≈150 г × ≈53 кк/100 г
• Сир 150 кк = 100 г × 150 кк/100 г

За день: 1090 кк
```

Якщо є природне UI-представлення порції, використовується спеціальний шаблон:

```text
Яйця ≈140 кк = 2 шт.
```

Для однієї позиції маркер не додається. Для двох і більше позицій спочатку
показується назва й загальна калорійність страви без маркера, а кожен складник
форматується окремим рядком із префіксом `• `. Це правило визначається кількістю
`items` у перевіреному `MealResult`, а не текстом від LLM.

Кнопка `Видалити` і чинний callback-контракт зберігаються.

## 8. Денна ціль

### 8.1. Дані

До реєстру користувачів останньою колонкою додається:

```text
daily_kcal_goal
```

Порожня клітинка означає, що ціль не встановлена. Інше значення — додатне ціле
число в дозволеному діапазоні.

Потрібна явна міграція чинного заголовка реєстру: додати нову колонку без зміни
наявних клітинок. Код після міграції має, як і зараз, відхиляти невідому або
переставлену схему.

`UserRecord`, `UserRegistry` та тестові реалізації розширюються читанням і
перевірюваним записом цілі. Зміна цілі не повинна залишати застаріле значення в
кешованому `UserManager` або `CaloriesService`.

### 8.2. Команда і стан

Підтримуються:

```text
/goal
/goal 2000
```

`/goal` переводить приватний чат у короткочасний стан очікування наступного
текстового повідомлення з цілим числом або дії вимкнення. Поки цей стан
активний, повідомлення не передається аналізатору їжі.

Якщо ціль уже є, відповідь `/goal` містить inline-кнопку `Вимкнути ціль`.
Callback прив’язаний до поточного користувача, детерміновано записує порожнє
значення `daily_kcal_goal` і не викликає LLM.

Стан зберігається в Telegram `user_data`, не є бізнес-даними й може бути
втрачений після перезапуску. Інша команда скасовує очікування. Після успішного
запису, вимкнення або скасування стан очищається.

Валідація числа й тексти помилок є детермінованими. Запис у реєстр має бути
перевірений повторним читанням або еквівалентною гарантією.

### 8.3. Використання цілі

- Без цілі показується лише денний підсумок.
- До досягнення цілі показується невід’ємний залишок.
- Після перевищення цілі залишок не показується.
- Ціль не змінює записані калорії та не використовується LLM.

## 9. `/week`

`MealStore` отримує операцію читання діапазону облікових дат або готових денних
сум. Google Sheet для одного звіту читається один раз, після чого рядки
групуються в пам’яті за збереженою колонкою `day`.

Період:

```text
current_accounting_day - 6 днів ... current_accounting_day
```

Формат відповіді:

```text
Останні 7 днів

• 02.08: 1640 кк
• 03.08: 1800 кк
• 04.08: немає записів
• 05.08: 1870 кк
• 06.08: 1730 кк
• 07.08: немає записів
• 08.08: 2310 кк

Заповнено: 5 із 7 днів
У середньому: 1870 кк/день
Денна ціль: 2000 кк
У межах цілі: 4 із 5 заповнених днів
Найменше: 1640 кк
Найбільше: 2310 кк
```

Правила обчислення:

- сумувати точні `meal_kcal` кожного дня та округлювати денний результат після
  сумування;
- сформувати для UI всі сім послідовних дат у хронологічному порядку;
- для заповненої дати показати округлену денну суму у форматі
  `• DD.MM: N кк`;
- для дати без рядків показати `• DD.MM: немає записів`;
- не підставляти нульове споживання для порожніх дат у статистичних
  розрахунках;
- середнє рахувати за кількістю заповнених днів;
- мінімум і максимум рахувати за заповненими днями;
- `days_within_goal` рахувати лише серед заповнених днів;
- використовувати поточну ціль на момент запиту, без історії змін цілі.

LLM для `/week` не викликається.

## 10. Контент і Telegram-команди

Користувацькі тексти зберігаються в UTF-8 файлах окремо від Python-коду:

```text
calories_bot/start.txt
calories_bot/help.txt
calories_bot/tips.txt
calories_bot/admin_help.txt
```

Файли перечитуються при відповідній команді, тому зміна тексту не вимагає зміни
Python-коду. Відсутній або порожній файл не повинен спричиняти необроблений
виняток: помилка логується, користувач отримує короткий безпечний резервний текст.

Глобальне Telegram-меню:

```text
/day
/week
/goal
/help
/tips
```

Меню адміністратора містить ці команди та чинні admin-команди. `/start` не
потрібно додавати в command menu.

## 11. Повідомлення про помилки

Повідомлення вибираються кодом за типом помилки, а не генеруються LLM:

- помилка детермінованого формату;
- повідомлення не описує їжу;
- невдалий або невалідний LLM-аналіз;
- нерозпізнане фото;
- помилка читання Google Sheets;
- підтверджена відмова запису;
- невизначений результат запису;
- помилка зміни цілі;
- помилка тижневого звіту.

Тексти мають бути короткими, без цитування початкового повідомлення. Лише
невизначений результат запису може просити перевірити таблицю перед повторним
надсиланням відповідно до чинного контракту.

## 12. Міграція і сумісність

1. Додати `daily_kcal_goal` в кінець заголовка реєстру користувачів; існуючі
   значення залишити порожніми.
2. Нові поля `items_json` зробити необов’язковими при читанні старих рядків.
3. Не змінювати чинні `telegram_message_id`, `day`, фото-шляхи або розраховані
   історичні значення.
4. Повторне відображення старого дубльованого update має працювати з legacy
   `items_json`.
5. Додати нові контент-файли й не включати до них секрети або конфігурацію.

Автоматична міграція має приймати тільки точно відому попередню схему. Невідома
схема завершується контрольованою помилкою без зміни таблиці.

## 13. Тестування

### 13.1. Детерміновані unit-тести

- нормалізація одиниць, чисел словами, `#` і `ккал/100 г`;
- збереження `2 яйця` як кількості та `піца 30 см` як діаметра;
- source ID, пропущені, неправильні й дубльовані джерела;
- пріоритет явних значень над LLM і фото;
- походження значень та правила `≈`;
- арифметика й `ROUND_HALF_UP`;
- усі шаблони компактної відповіді та HTML escaping;
- читання, зміна, вимкнення й міграція денної цілі;
- стан очікування `/goal` і недопущення LLM-виклику;
- семиденний діапазон, порожні дні, мінімум, максимум, середнє і межа
  `day_start`;
- сім рядків `/week` у хронологічному порядку, включно з текстом для порожніх
  дат;
- усі мапінги помилок;
- backward compatibility старого `items_json`.

### 13.2. Інтеграційні тести без реального LLM

Використовувати fake analyzer і fake registry/store для перевірки повного
сценарію повідомлення, фото, дубля, запису, `/goal`, `/week` та видалення.

### 13.3. LLM eval-набір

Окремий стабільний набір перевіряє тільки недетерміновану частину:

- природні українські та поширені російські описи;
- побутові порції;
- відсутню вагу або калорійність;
- кілька явно названих складників;
- фото страви з caption і без нього;
- фото етикетки;
- повідомлення, яке не є їжею;
- зображення, на якому неможливо впевнено визначити їжу.

Для кожного прикладу фіксуються обов’язкові інваріанти й допустимі діапазони, а
не одне точне модельне число. До зміни промпту зберігається baseline. Зміна
приймається лише тоді, коли покращує цільові сценарії без суттєвої регресії.

Реальні персональні фото користувачів не додаються до Git. Eval-фото мають бути
тестовими й не містити персональних або секретних даних.

## 14. Спостережуваність

- Зберегти чинні метадані моделі, використання токенів і вартість.
- Логувати тип помилки валідації, модель і source IDs без base64 фото,
  Telegram token, API keys або вмісту секретних файлів.
- Окремо рахувати помилки нормалізації, LLM, post-validation, Sheets read/write
  та `/goal`/`week`.
- Не логувати повні фотографії чи URL Telegram Bot API.

## 15. Критерії готовності

- Усі критерії з `docs/NEXT_VERSION_PRODUCT.md` виконані.
- Детермінована логіка має unit-тести й не потребує LLM у тестах.
- Явні значення користувача неможливо змінити відповіддю моделі.
- LLM не виконує арифметику, статистику, форматування або роботу з ціллю.
- Текст, фото страви й етикетка проходять єдиний перевірюваний pipeline.
- Невалідна відповідь або неправдоподібні значення не створюють запису.
- Міграція реєстру не змінює наявні дані й відхиляє невідому схему.
- `/goal` і `/week` ізольовані між користувачами та враховують `day_start`.
- `/week` показує кожну із семи дат, але не включає порожні дні в статистику.
- Контент `/start`, `/help`, `/tips` змінюється незалежно від Python-коду.
- Повний чинний набір тестів проходить без регресій у доступі, таблицях, фото,
  дедуплікації, видаленні й адмініструванні.
