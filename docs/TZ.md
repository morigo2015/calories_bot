# Технічне завдання: багатокористувацька версія Telegram-бота обліку калорій

## 1. Мета

Переробити Telegram-бота з режиму одного користувача на закритий багатокористувацький режим приблизно для 10–15 користувачів.

Кожен користувач:

- працює з ботом тільки у власному приватному Telegram-чаті;
- має окремий Google Spreadsheet з історією прийомів їжі;
- має окрему локальну директорію фотографій;
- має власну межу початку облікового дня;
- не бачить і не отримує інформацію про інших користувачів.

Усі персональні Google Spreadsheets зберігаються в одній Google Drive-папці бота.

Для керування користувачами використовується окремий адміністративний Google Spreadsheet.

Окрема база даних, web-admin, користувацькі акаунти, паролі або OAuth не потрібні.

## 2. Ідентифікація користувача

Основним ідентифікатором користувача є:

```text
telegram_user_id
```

Перед будь-яким:

- викликом LLM;
- читанням або записом персонального Google Spreadsheet;
- обробкою `/day`;
- збереженням фото;
- видаленням запису

бот повинен спочатку визначити користувача за `telegram_user_id` та отримати його персональний контекст.

Персональний контекст містить:

- `telegram_user_id`;
- `status`;
- `spreadsheet_id`;
- `day_start`;
- шлях до персональної директорії фотографій.

Telegram username, display name та `chat_id` не використовуються як ключ власника даних.

## 3. Telegram-чати

Звичайний користувач може працювати з ботом тільки у приватному чаті:

```text
chat.type = private
```

Ігноруються:

- групи;
- супергрупи;
- канали;
- edited-message updates.

Адміністратор також працює з ботом через приватний чат.

## 4. Реєстр користувачів

Використовується окремий Google Spreadsheet.

Його ID задається:

```text
USERS_SPREADSHEET_ID
```

Схема реєстру:

| Колонка | Зміст |
|---|---|
| `telegram_user_id` | Telegram ID; порожній до активації |
| `display_name` | ім'я, задане адміністратором |
| `telegram_username` | username на момент активації, інформаційно |
| `status` | `invited`, `active` або `blocked` |
| `invite_token` | token неактивованого invite |
| `spreadsheet_id` | ID персонального Spreadsheet |
| `day_start` | початок облікового дня у форматі `HH:MM` |

Підтримуються три стани.

### `invited`

Запрошення створено, але користувач ще не завершив активацію.

### `active`

Користувач має доступ до бота.

### `blocked`

Доступ вимкнено, але персональні дані зберігаються.

В одного `telegram_user_id` не повинно одночасно існувати більше одного користувача зі статусом `active` або `blocked`.

Окрема база даних не створюється.

## 5. Google Drive

У конфігурації задається:

```text
GOOGLE_DRIVE_FOLDER_ID
```

У цій папці зберігаються:

- адміністративний Spreadsheet реєстру;
- персональні Spreadsheets користувачів.

Персональний Spreadsheet створюється під час активації invite.

Рекомендована назва:

```text
<display_name> — <telegram_user_id>
```

Назва потрібна тільки для зручності адміністратора.

Уся програмна логіка використовує `spreadsheet_id`.

## 6. Адміністратор

Адміністратор визначається конфігурацією:

```text
ADMIN_TELEGRAM_USER_ID
```

Підтримуються admin-команди:

```text
/invite <display_name>
/block <telegram_user_id>
/unblock <telegram_user_id>
/delete <telegram_user_id>
```

Вони виконуються тільки якщо:

```text
message.from.id == ADMIN_TELEGRAM_USER_ID
```

Admin-команди не потрібно реєструвати в Telegram command menu.

## 7. Створення invite

Команда:

```text
/invite Вася
```

повинна:

1. створити випадковий непрогнозований `invite_token`;
2. додати рядок у реєстр зі статусом `invited`;
3. записати `display_name`;
4. встановити:

```text
day_start = DEFAULT_DAY_START
```

5. залишити `telegram_user_id` і `spreadsheet_id` порожніми;
6. повернути адміністратору deep link:

```text
https://t.me/<bot_username>?start=<invite_token>
```

Invite:

- одноразовий;
- не має автоматичного строку дії;
- може активувати одного Telegram-користувача.

Адміністратор за потреби може вручну змінити `day_start` у реєстрі.

## 8. Активація користувача

При:

```text
/start <invite_token>
```

бот:

1. знаходить рядок зі статусом `invited` і відповідним token;
2. перевіряє, що цей `telegram_user_id` ще не має `active` або `blocked` запису;
3. створює персональний Google Spreadsheet, якщо він ще не був створений;
4. створює в ньому актуальну meal-схему;
5. записує в invite-рядок:
   - `telegram_user_id`;
   - `telegram_username`;
   - `spreadsheet_id`;
6. як останній крок:
   - встановлює `status=active`;
   - очищає `invite_token`;
7. показує користувачу коротку довідку.

Статус `active` виставляється тільки після того, як персональний Spreadsheet створено і його ID збережено в реєстрі.

Складна транзакційність не потрібна.

Якщо активація перервалася до встановлення `active`, invite залишається неактивованим. Якщо в його рядку вже є `spreadsheet_id`, повторна спроба повинна повторно використати цей Spreadsheet, а не створювати новий.

Невідомий користувач без валідного invite отримує:

```text
Доступ лише за запрошенням.
```

Повторний `/start` активного користувача не створює нового Spreadsheet і показує звичайну довідку.

## 9. Персональний Google Spreadsheet

Кожен активний або blocked-користувач має окремий Google Spreadsheet.

Схема:

| Колонка | Зміст |
|---|---|
| `timestamp` | числовий date-time Google Sheets у `APP_TIMEZONE` |
| `day` | дата облікової доби `yyyy-mm-dd` |
| `meal_name` | назва прийому їжі |
| `total_weight_g` | загальна вага |
| `meal_kcal` | калорії прийому |
| `kcal_per_100g` | агрегована калорійність на 100 г |
| `telegram_message_id` | ID користувацького Telegram-повідомлення |
| `normalized_request` | нормалізований текст або caption |
| `request` | оригінальний текст або caption |
| `photo_path` | абсолютний локальний шлях або порожнє значення |
| `items_json` | структуровані складники та ознаки оцінки |
| `estimated` | чи містяться оцінені значення |
| `model` | модель аналізу |
| `effort` | effort аналізу |
| `input_tokens` | використані input tokens |
| `output_tokens` | використані output tokens |
| `llm_cost_usd` | розрахована вартість, якщо задані тарифи |

Один користувацький запит створює максимум один рядок.

Денний підсумок окремо не зберігається.

Усі meal-операції повинні отримувати `spreadsheet_id` із персонального контексту поточного користувача.

Спільного meal-spreadsheet для всіх користувачів бути не повинно.

## 10. Обліковий день

Часовий пояс залишається глобальним:

```text
APP_TIMEZONE
```

Наприклад:

```text
Europe/Kyiv
```

Стандартна межа дня:

```text
DEFAULT_DAY_START=01:00
```

У кожного користувача фактичне значення береться з `day_start` у реєстрі.

Для:

```text
day_start=01:00
```

повідомлення до `00:59:59` належать попередньому обліковому дню, а повідомлення з `01:00:00` — новому.

Перехід літнього та зимового часу обробляється через `APP_TIMEZONE`.

При створенні запису обчислена дата зберігається в колонці `day`.

Якщо адміністратор пізніше змінює `day_start`, раніше збережені значення `day` автоматично не перераховуються.

## 11. Фото

Для кожного користувача використовується окрема директорія:

```text
PHOTO_STORAGE_DIR/<telegram_user_id>/
```

Наприклад:

```text
/photos/123456789/
/photos/987654321/
```

Фото зберігається як JPEG.

У персональний Google Spreadsheet записується абсолютний `photo_path`.

Видалення локального фото дозволено тільки якщо canonical path знаходиться всередині:

```text
PHOTO_STORAGE_DIR/<telegram_user_id>/
```

Зовнішні шляхи не видаляються.

## 12. Обробка їжі

Зберегти існуючу функціональність:

- текстових описів;
- нормалізації одиниць;
- явної ваги;
- явної калорійності;
- оцінки відсутніх параметрів;
- аналізу фото;
- фото з caption;
- фото без caption;
- тристрокової відповіді;
- `/day`;
- кнопки `Видалити`.

Явні дані користувача мають пріоритет над оцінкою.

До виклику LLM обов'язково перевіряється доступ користувача.

Для невідомого або blocked-користувача:

- LLM не викликається;
- фото не завантажується;
- персональний Spreadsheet не читається і не змінюється.

Blocked-користувач отримує:

```text
Доступ до бота вимкнено.
```

## 13. Захист від дублювання

`telegram_message_id` перевіряється всередині персонального Spreadsheet поточного користувача.

Повторна доставка одного Telegram update не повинна створювати другий рядок.

Пошук за `telegram_message_id` виконується тільки після визначення користувача та його `spreadsheet_id`.

Глобальний складений ID для meal-записів не потрібен.

## 14. Видалення окремого прийому їжі

Кожна успішна відповідь має inline-кнопку:

```text
Видалити
```

Callback не повинен містити `spreadsheet_id` іншого персонального контексту або дозволяти вибрати довільного користувача.

При callback:

1. власник визначається через `callback.from.id`;
2. відкривається тільки його персональний Spreadsheet;
3. потрібний рядок знаходиться за `telegram_message_id`;
4. з рядка береться `day`;
5. рядок фізично видаляється;
6. локальне фото видаляється, якщо воно належить персональній директорії;
7. підсумок для цього `day` перераховується;
8. відповідь бота змінюється на:

```text
Видалено
=== N кк
```

Початкове повідомлення користувача в Telegram не видаляється.

Якщо Google Sheets не підтвердив видалення, Telegram-повідомлення не змінюється.

Повторний callback має бути ідемпотентним.

## 15. Блокування

Команда:

```text
/block <telegram_user_id>
```

переводить:

```text
active → blocked
```

При цьому:

- Spreadsheet залишається;
- фото залишаються;
- історія залишається;
- нові запити не обробляються.

Команда:

```text
/unblock <telegram_user_id>
```

переводить:

```text
blocked → active
```

і користувач продовжує працювати з тим самим Spreadsheet.

## 16. Повне видалення користувача

Команда:

```text
/delete <telegram_user_id>
```

доступна тільки адміністратору.

Перед фактичним видаленням бот показує inline-підтвердження.

Після підтвердження:

1. користувач переводиться в `blocked`;
2. видаляється його персональний Google Spreadsheet;
3. видаляється його локальна директорія фото;
4. тільки після успішного завершення цих операцій рядок користувача фізично видаляється з адміністративного реєстру.

Складна транзакційність не потрібна.

Якщо видалення перервалося або завершилося помилкою:

- рядок користувача залишається в реєстрі;
- його статус залишається `blocked`;
- адміністратор отримує повідомлення про помилку;
- `/delete` можна виконати повторно.

При повторній спробі вже відсутній Spreadsheet або photo directory вважаються вже успішно видаленими.

Після повного delete людина більше не є користувачем системи. Її можна запросити заново через новий invite.

## 17. Telegram-команди

Для звичайного користувача:

```text
/start
/help
/day
```

Через Telegram Bot API під час запуску глобально реєструються тільки:

```text
/day
/help
```

Тому після введення `/` користувач бачить `/day` та `/help`.

Admin-команди не реєструються в command menu і вводяться адміністратором вручну.

## 18. Відповіді без цитування

Бот не використовує reply/quote на початкове повідомлення користувача.

Це правило діє для:

- успішних результатів;
- помилок;
- `/start`;
- `/help`;
- `/day`;
- повідомлень про доступ;
- admin-команд.

## 19. Перехід існуючого користувача

Для поточного користувача не потрібно створювати новий Spreadsheet або копіювати історію.

Під час переходу:

1. створити для нього рядок у реєстрі;
2. встановити `status=active`;
3. записати його `telegram_user_id`;
4. записати існуючий `spreadsheet_id`;
5. встановити його `day_start`.

Якщо його персональна таблиця має точну підтримувану legacy-схему без колонки `day`, застосувати наявну міграцію зі збереженням усіх клітинок та дозаповненням `day`.

Якщо існуючі фотографії зберігаються без персональної піддиректорії:

1. перенести їх у:

```text
PHOTO_STORAGE_DIR/<telegram_user_id>/
```

2. оновити відповідні `photo_path` у Google Sheet.

Інші невідомі схеми таблиць автоматично не мігрувати.

## 20. Критерії готовності

Доробка вважається завершеною, якщо:

- новий користувач активує доступ через персональний invite;
- invite є одноразовим;
- повторний `/start` не створює нового Spreadsheet;
- для кожного користувача використовується окремий Spreadsheet;
- усі персональні Spreadsheets знаходяться в одній Drive-папці;
- дані користувачів не змішуються;
- `/day` читає тільки дані поточного користувача;
- персональний `day_start` правильно впливає на облікову дату;
- фото зберігаються в окремих персональних директоріях;
- невідомі та blocked-користувачі не запускають LLM;
- block/unblock не видаляють історію;
- delete видаляє Spreadsheet, локальні фото та рядок із реєстру;
- невдалий delete залишає користувача blocked і дозволяє повторити операцію;
- повторний Telegram update не створює дубль;
- admin-команди не можуть виконувати звичайні користувачі;
- `/day` і `/help` доступні через Telegram command menu;
- стандартна функціональність тексту, фото, `/day` та `Видалити` працює незалежно для кожного користувача.
